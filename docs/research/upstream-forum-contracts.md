# Upstream forum contracts for the SDK extraction

Research for [Which upstream forum contract changes affect the SDK?](https://github.com/Benson-mk/tsdm-sdk/issues/2), 18 November 2026, Hong Kong.

Two upstream test-forum samples expose a reproducible gap in `@tsdm/forum-client` 0.26.0. The SDK rejects populated board and thread responses that contain structured fields and omit the page’s HTML `document`. It reads nine posts from an older thread response that includes the HTML. Other first-release candidates include capability discovery, unread-notice pagination and structured write outcomes. Their value and side effects differ by operation. ## Operation comparison

**Discovery and opt-in.** The SDK’s ordinary page request adds `tsdmapp=json`. Upstream requests `nodoc=1` with normal JSON-mode pages, so a structured response can omit the document. Plugin 4 adds a separate `tsdmv=4` opt-in for named capabilities. Upstream checks the `status` reply for `v4: 1`, then the relevant feature flag or list entry. It treats actions of a known plugin older than 3.5.0 as unavailable. The statement that a request without `tsdmv=4` receives the 3.9 representation applies to the newly gated operations. Board and thread structured reads predate that switch. Qualification needs old, off, partially advertised and differently shaped responses for each selected operation. The app’s minimum version is one consumer’s policy. [SDK request](https://github.com/Benson-mk/tsdm-ui/blob/94f68a5558d016d561b2bac417db2f52b5d27510/src/forum-client/index.ts#L886-L921) · [Upstream page query](https://github.com/Carinoasd/tsdm_client/blob/02df67e39ded906def5b868e8f8311ba735b316c/lib/features/tsdmapp/tsdmapp_api.dart#L788-L825) · [Plugin policy](https://github.com/Carinoasd/tsdm_client/blob/02df67e39ded906def5b868e8f8311ba735b316c/lib/features/tsdmapp/tsdmapp_api.dart#L78-L94) · [Per-operation flags](https://github.com/Carinoasd/tsdm_client/blob/02df67e39ded906def5b868e8f8311ba735b316c/lib/features/tsdmapp/v4.dart#L80-L117)

**Boards and threads.** Upstream builds boards from structured forum fields and threads from structured post rows, with a legacy document path for each. The SDK’s board reader parses the HTML for its viewer and rows. Its thread reader can use the envelope’s viewer and thread ID, then still needs a document to find post content. Simply adding `nodoc=1` would expose the failures below. The first-release decision needs to cover returned board/thread identity, viewer permissions, empty versus incomplete lists, filtering, pagination and per-post content where supported. The experiment establishes a decoder difference for document-free data. The SDK’s existing, document-requesting path may continue to work on a particular deployment. [Upstream board reader](https://github.com/Carinoasd/tsdm_client/blob/02df67e39ded906def5b868e8f8311ba735b316c/lib/features/forum/repository/forum_repository.dart#L20-L63) · [Upstream thread reader](https://github.com/Carinoasd/tsdm_client/blob/02df67e39ded906def5b868e8f8311ba735b316c/lib/features/thread/v1/repository/thread_repository.dart#L242-L265) · [SDK thread identity and content](https://github.com/Benson-mk/tsdm-ui/blob/94f68a5558d016d561b2bac417db2f52b5d27510/src/forum-client/read-thread.ts#L459-L515)

**Notices and acknowledgement.** The SDK exposes an explicit category/page read and restricts subsequent destinations to links offered on that list. It warns that even a failed or stale read may have marked notices read, and generic page reads refuse that route. Upstream’s separate `notify` operation can fetch an unread time window. With advertised `notify_paging`, it follows `has_more` and `next` using `limit` and `before`, checks the viewer on later pages, and deduplicates by ID. A busy reply that outlasts its wait budget ends this poll without falling back to the effectful page. For an incomplete or stalled scan the consumer withholds the notice acknowledgement. After a completed window it may separately post `seen` using the server clock and form hash. Clearing the new-private-message prompt is a separate flag. An SDK refresh needs to distinguish category history, unread observation and an explicit acknowledgement, including partial data, account changes and clock boundaries. The server-side extent of acknowledgement on a deployed account remains unverified. [SDK notices](https://github.com/Benson-mk/tsdm-ui/blob/94f68a5558d016d561b2bac417db2f52b5d27510/src/forum-client/index.ts#L403-L458) · [SDK route guard](https://github.com/Benson-mk/tsdm-ui/blob/94f68a5558d016d561b2bac417db2f52b5d27510/src/forum-client/index.ts#L868-L876) · [Polling and 429](https://github.com/Carinoasd/tsdm_client/blob/02df67e39ded906def5b868e8f8311ba735b316c/lib/features/notification/repository/notification_repository.dart#L399-L468) · [Pagination](https://github.com/Carinoasd/tsdm_client/blob/02df67e39ded906def5b868e8f8311ba735b316c/lib/features/notification/repository/notification_repository.dart#L510-L630) · [Acknowledgement conditions](https://github.com/Carinoasd/tsdm_client/blob/02df67e39ded906def5b868e8f8311ba735b316c/lib/features/notification/repository/notification_repository.dart#L753-L759) · [Acknowledgement request](https://github.com/Carinoasd/tsdm_client/blob/02df67e39ded906def5b868e8f8311ba735b316c/lib/features/notification/repository/notification_repository.dart#L805-L820)

**Posting and result checks.** The SDK’s ordinary publication prepares against a native form, requests its AJAX response, removes `tsdmapp` from the submit URL, and treats a returned destination as a candidate for independent stored-source verification. Rating, reporting and search already recognize selected schema-13 results. Upstream can read structured post forms when available, requests JSON write results, and interprets reply-specific keys, moderation, refusals and redirects. The capability-gated favorite dialog is another concrete example. An inconclusive favorite outcome can trigger a bounded list readback. The refresh decision needs to specify which result shapes only identify a candidate, how to report uncertain dispatch, and what independent observation permits a public success result. No form was submitted in this research. **Adjacent operations.** Upstream reads search results (schema 6), favorites (8) and private conversations (11) from structured fields. The corresponding SDK readers still consume document HTML. These are candidates even if board and thread support ships first. The upstream attachment implementation also describes group-restricted downloads that need the correct account session on the canonical forum host. The SDK delegates file transport to the host and distinguishes refused permissions and redirected or incomplete bytes. A host/session difference needs a separate qualification case before claiming a download regression. **Areas with no demonstrated regression.** Both readers still use ordinary forum page routes and retain a document path. The legacy thread sample below successfully traverses the SDK’s existing path. Upstream’s new operating-system shortcuts and desktop window controls do not introduce a new forum operation in the cited release. There is no evidence here that an account using the SDK’s current request shape has lost access to boards, threads, or attachments in production. ## Offline comparison

Run in a scratch directory containing the extracted SDK tarball (`package/index.js`). Set `FIXTURES` to `test/data/tsdmapp` from the pinned upstream revision. The probe used Node v26.0.0, in-memory HTTP 200 envelopes and the synthetic origin embedded in the legacy sample. All three calls issued one request with `tsdmapp=json`. The origin must match the legacy document’s canonical link for its thread identity check to pass.
```sh
node --input-type=module - <<'NODE'
import { readFileSync } from 'node:fs'
import { createForumClient } from './package/index.js'

const origin = 'https://forum.test'
const cases = [
  ['thread_plain.json', 'mod=viewthread&tid=9199345'],
  ['forum_v2_fid12.json', 'mod=forumdisplay&fid=12'],
  ['thread_v3_long_p1.json', 'mod=viewthread&tid=1120'],
]
for (const [name, query] of cases) {
  const body = readFileSync(process.env.FIXTURES + '/' + name, 'utf8')
  const requests = []
  const transport = {
    async request(url) {
      requests.push(new URL(url).search)
      return { url, body, status: 200, contentType: 'application/json' }
    },
  }
  const result = await createForumClient({ origin, transport })
    .readPage(origin + '/forum.php?' + query)
  console.log(name, requests, result.kind, result.thread?.posts.length ?? '')
}
NODE
```

The three fixtures give a repeatable comparison at the public entry point. Their coverage is limited to those payloads. All other operation findings above come from source inspection. A production plugin version, its enabled features per account and the current effects of any write remain open evidence requirements for the release decision.
