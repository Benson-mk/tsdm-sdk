# Qualify the release tarball and record carried-forward evidence

For `0.1.0`, establish a baseline covering every operation in the approved inventory. A consumer journey can cover several operations when it checks each result. On later releases, revalidate operations affected by the change, including dependencies on shared transport and parsing. For each carried-forward result, identify the last verified version and explain why the change leaves that operation unaffected. This saves repeated manual checks and makes their reliability depend on tracing indirect changes. A full automated end-to-end run is welcome when available.

For every release, verify the candidate tarball against the manifest, install it in a clean Node.js 26.x project, exercise the `tsdm-sdk` public import and type-check its declarations. Use the minimal guest-read example in the release README for the routine live check. As a signed-out guest, read a public board and open a thread returned by that board. A browser or `curl` exercises the forum API directly. Running the example through the installed SDK also exercises the package. The Python `requests` and `curl` guide remains a deliverable. Users can try the guest read without fixtures or dedicated test tools.

Archived results apply to their recorded artifacts. Controlled transport establishes the candidate's behavior for the supplied responses. A host handoff can establish the destination the SDK gives the host. Deployment-specific claims require observations under the applicable deployment and session. The routine live check establishes a public read without changing forum state. Skip live posts when the posting workflow and its dependencies are unchanged. When they change, assess whether the affected behavior needs a live post.

Keep a small versioned qualification record in the SDK repository and link it from the release notes. Record the candidate version and tarball SHA-256, checks run, commands and prerequisites, pinned inputs where applicable, and expected and observed results. Distinguish checks run against the candidate from results carried forward. For the live guest read, record the date, deployment, board and returned thread. The issue records release blockers, example journeys and the trade-offs. [Maintainer resolution](https://github.com/Benson-mk/tsdm-sdk/issues/7#issuecomment-6982631888)
